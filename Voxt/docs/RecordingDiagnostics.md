# Recording diagnostics

Enable recording diagnostics in General settings when investigating a voice-input failure. The setting defaults off, persists across launches, and remains enabled until you turn it off. There is no fifteen-minute timer. Recording diagnostics neither enables history audio storage nor uploads telemetry.

The existing log viewer and export action show typed JSON events. Records contain closed event, backend, outcome and error classifications; random session/request/runtime identifiers; observed counts; monotonic elapsed milliseconds; and a wall-clock timestamp. The export header contains only schema version, numeric macOS version, enablement and write-failure status. Audio, transcript, prompt, generated text, clipboard, selected text, window titles, URLs, custom model names, private paths, credentials and hashes of user content are excluded.

Both swift-log handlers reject arbitrary messages and metadata, even when a caller requests visible/preview logging. Legacy free-form lines already on disk are filtered from the viewer and export. Legacy warnings/errors retain category and severity as `legacyDiagnostic` placeholders without evaluating private message text; legacy info/debug calls are not persisted. Their information remains deliberately limited. New app, model download/load/release, history persistence and credential failures use typed events instead. Existing model/hotkey debug switches independently enable typed routing, timing, download and shortcut events; the switches never enable arbitrary strings. The developer LLM smoke command no longer prints prompt, response, model identifier or raw errors, and the llama callback no longer forwards raw C error messages to stderr.

Events cover recording start, input preparation/readiness, stop, failed start, cancellation and cleanup; first partial and final/empty/failed ASR results; capture and VAD summaries and fallback; Omni process start, readiness/model loading, exit and release; individual HTTP/live requests; enhancement execution; and text-delivery attempts. Runtime events carry a runtime ID without a recording session. Request events carry both IDs when the caller has a recording session. Background meeting summaries are unscoped. A native server's readiness is also the observable model-load completion boundary.

`asrReceivingAudio` means the client has handed actual audio to the ASR path or begun a file submission; it does not assert a remote server acknowledgment. Streaming capture reports observed callback/sample counts. File-based remote capture omits those counts because AVAudioRecorder does not expose them. StepFun and Gemini startup-buffer drops are accumulated as chunks/bytes and reported in the capture summary. VAD speech/fallback counts are not dropped-audio counts. `shortcutPosted` means paste key events were posted; it does not establish that another application accepted the text.

The rolling store retains the existing default of a 2 MiB current file and five 2 MiB archives. It rotates instead of disabling diagnostics. Individual oversized lines are rejected, and write failures appear in the export header. Previously migrated legacy files are not part of the active rolling set. PR #15 separately adds quota controls and broader storage accounting; these diagnostics changes do not depend on that PR.

No per-frame or per-token diagnostic writes are added. Disabled recording avoids evaluating event payloads. The recorder bounds session/request bookkeeping, deduplicates terminal and first-partial events, and excludes late session callbacks after cleanup even after more than 256 later sessions. Independent request/resource cleanup can still be reported after recording cleanup. Enabling diagnostics during an existing recording starts session-stage collection with the next recording, avoiding an invented session start. App termination records cancellation and cleanup for an active recording. ASR, enhancement or insertion failures remain failures in the final session outcome even when partial ASR text is salvaged. Dictation classifies Speech errors and finalization timeouts independently of displayed/delivered partial text; generation identifiers reject callbacks from a prior recognizer. Capture callbacks keep their existing in-memory counters; the first Dictation audio event is dispatched away from the audio callback. File output uses the existing utility queue.

## Isolated automated checks

From the Voxt project directory:

```sh
bash tools/test_recording_diagnostics.sh
bash tools/test_recording_diagnostic_handlers.sh /path/to/pinned/swift-log
```

The second checkout must match `Package.resolved` (swift-log 1.15.1, revision `9c6fb14227f55d8f711ce3847dc2f419fb0ecacb`). Both runners compile production files with Swift 5 language mode and MainActor default isolation. They use temporary directories and new UserDefaults suites and do not instantiate the app, access real history, record a microphone or alter permissions.

The runtime test decodes the repository's Qwen FLAC fixture and passes its samples through the production multipart/SSE client to a local fake server. It covers success, empty output, HTTP failure, cancellation, startup timeout and sensitive stderr, including resource retirement. It needs loopback binding permission. The VAD test compiles the production planner, frame decider and statistics with injected backend failures to exercise timeout, energy fallback and release. The core test exercises the production viewer/export with synthetic legacy secrets. The handler test compiles actual swift-log, the production facade logger and multiplex handler plus both production sinks and injects an OSLog test sink, so it does not inspect system logs. Hosted `SpeechDiagnosticCompletionTests` inject callbacks into the same completion path used by Speech.framework without constructing a recognizer or audio engine. `VoxtLoggerTests` verifies independent hotkey/model preferences and disabled payload evaluation. These checks do not replace an Xcode app build or real-model acceptance.

Full validation still requires the shared Voxt Xcode scheme. On a machine with the complete Xcode toolchain, run the documented unsigned build and tests, then manually verify the setting, a real microphone session, cancellation, log viewing/export and cross-application paste. No fixture/mock result establishes microphone, system-permission, global-hotkey or target-application behavior.
